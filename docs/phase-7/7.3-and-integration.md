# 7.3 Public trips and destinations, and the Phase 7 integration

## What the site does now

- `/en/trips`, `/de/reisen`: list with filters (style, length, budget, destination). A plain GET form, so it works
  without JavaScript. Filtered views point their canonical at the plain list.
- `/en/trips/<slug>`, `/de/reisen/<slug>`: trip page. Itinerary, highlights, included / not included, gallery,
  related trips, planner link carrying `?trip=<slug>` (stored with the lead). No price or availability is promised.
- `/en/destinations`, `/de/reiseziele` and the five destination pages (`gizeh`, `assuan`, ...): summary, facts,
  published trips that visit the place, planner link. German texts are a first draft: native review needed.
- Home sections (featured trips, choose your journey) read through the same layer.
- Sitemap is dynamic (pages, destinations, visible trips with `lastModified`); hreflang only for languages in
  which a trip is visible; breadcrumbs + TouristTrip structured data; language switcher maps to the translated
  slug (trip) or localized destination slug, and falls back to the list.
- An old trip slug answers with a permanent redirect (from `redirects`), only when the target is visible.
  Unknown slugs are a real 404. No English fallback on German pages.

## One read layer

`src/content/public.ts` is the only trip read for public pages. `CONTENT_SOURCE=seed` builds the same shape from the
seed files; `database` reads `src/content/db/public-trips.ts` (cached, tags `trips` + `sitemap`, which the
dashboard's publish expires). A translation that fails validation is skipped and logged, never a site-wide error.

## Dashboard <-> site

- The dashboard store now writes the 7.2 tables (`trips`, `trip_translations`, `media_assets`, `trip_media`,
  `redirects`) plus `0003_dashboard_support.sql` (drafts allowed, `flexible_duration`, `audit_logs`).
  The old `0020` migration and `db:seed-trips` are gone: use `npm run content:seed`.
- Dashboard trip ids are UUIDs in the database (the in-memory dev store keeps its seed ids).
- Publish / unpublish / editing a live translation calls `updateTag("trips" | "sitemap" | "trip:<id>")`.
- Preview: dashboard link -> `/api/preview` (public host) -> cookie + Draft Mode. The proxy rewrites a trip address
  to `/[lang]/trips/<slug>/preview` only for a valid cookie; that page checks the cookie again.
- Slug changes write `redirects` rows (`old_path` -> current path, paths from the route map).

## Switches

- `SHOW_REVIEW_CONTENT=true` (default): "review" content is visible pre-launch. Set `false` at launch.
  NOTE: decision D10 says "off by default in production"; the default stays on so the current pre-launch site
  does not go empty. Flip it when the content is approved.
- `PREVIEW_SECRET` must be identical on the dashboard and the public deployment.

## Order to bring it up

1. `npm install && npm run format && npm run lint && npm run typecheck && npm test && npm run build`
2. `npm run db:migrate` (0002, 0003), `npm run content:seed`, `npm run content:verify`
3. Set `CONTENT_SOURCE=database`, `PREVIEW_SECRET`, the dashboard variables (see `.env.example`).
4. `npm run verify:routing -- --phase 7.3` against a running server.
5. In the dashboard: create a trip, add EN + DE, preview, publish; check the public page updates without a redeploy;
   change the slug and open the old address (expect a 308/301 to the new one).
