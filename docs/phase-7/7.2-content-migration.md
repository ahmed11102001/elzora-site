# Phase 7.2: content moved to Supabase (Postgres)

## What was added

| Part                                                                                                                                                     | Where                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Tables: `media_assets`, `trips`, `trip_translations`, `trip_media`, `redirects`                                                                          | `db/migrations/0002_content_platform.sql`                  |
| Leads: `trip_id`, `trip_slug`, `first_contacted_at`; statuses `new, contacted, qualified, proposal_sent, converted, lost` (`rejected` renamed to `lost`) | same file                                                  |
| `lead_activity`: every lead creation and status change, written by triggers; backfilled for existing leads                                               | same file                                                  |
| Row validation (Zod) and the seed ⇄ database mapping                                                                                                     | `src/content/db/schema.ts`, `src/content/db/mapping.ts`    |
| Cached database read (`"use cache"`, tag `trips`)                                                                                                        | `src/content/db/trips.ts`, `queries.ts`, `src/lib/db.ts`   |
| Source switch `CONTENT_SOURCE=seed                                                                                                                       | database`                                                  | `src/content/index.ts` |
| Import and verification                                                                                                                                  | `npm run content:seed`, `npm run content:verify`           |
| Trip context in leads                                                                                                                                    | planner reads `?trip=<slug>`; schema, submit, storage, CSV |

The public functions (`getTrips`, `getTrip`, …) keep their names and return the same shape, so no page or
component changed.

## How to run it

1. Back up or use a Supabase branch. Run `npm run db:migrate`.
2. `npm run content:seed -- --dry-run`, then `npm run content:seed`.
3. `npm run content:verify`. Every line must say PASS.
4. Set `CONTENT_SOURCE=database` (local `.env.local` first, then the deployment) and restart.
5. Compare `/en` and `/de` with what you saw before.

Rollback: unset `CONTENT_SOURCE`. The migration is additive; the only change to existing data is the
`rejected` → `lost` rename of the lead status.

## Decisions made

- **Statuses per translation.** The seed trips are all `review`, so both languages are `review`.
- **German slugs** are generated from the German title (for example
  `klassisches-aegypten-kairo-luxor-assuan`). The seed had none. They are only visible once the trip
  pages exist (7.3), and the dashboard can change them (with a 301) in 7.4. Check them.
- **German itineraries are empty.** The seed has no German itinerary text. A German translation with an
  empty itinerary is stored as `review` and is fine until publishing, where the dashboard will require it.
  The site behaves as before (itinerary text falls back to English).
- **All or nothing per list.** If a German list (highlights, itinerary…) has only some items translated,
  the import stops with a clear message instead of mixing items.
- **Re-running the import never overwrites** trips that already exist (so later dashboard edits are
  safe). `--update` overwrites them and is meant for development only.
- **Pre-launch visibility** is unchanged: `published` and `review` are visible. The environment switch of
  decision D10 arrives with the dashboard.
- **Failures are loud.** In database mode a failed read is an error; the seed is never used as a
  silent fallback. A wrong `CONTENT_SOURCE` value is an error too.

## Not verified here

- The SQL was not run against a database (none was available): run it on a Supabase branch first.
- `"use cache"`, `cacheTag` and `cacheLife("minutes")` follow Next.js 16 as documented, but were not
  compiled: `npm run typecheck` and `npm run build` are the check (see the 7.0 design, section 5).
- The unit tests prove the mapping: every seed trip survives seed → rows → site shape unchanged.
  `content:verify` proves the same against the real database.
